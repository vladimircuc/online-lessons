Part 0000
What this assignment is really testing

Most candidates read the brief and start designing slides. That is a trap. The trap is that the assignment looks like a lesson design exercise but it is actually a job audition where the lesson is the artifact. Read the rubric backwards.

The core insight

Forward Deployed Engineers at Deloitte will spend a chunk of every client engagement teaching, training, and explaining AI behavior to people who do not have an AI background. The take-home is testing whether you can do that on demand, in a mixed room, under pressure, with AI assistance. The topic, system prompts, is almost a coincidence. They want to see how you think about teaching anything.

What the panel sees

Three documents from you before the call (the brief, the AI reflection, the three discovery questions), then fifteen minutes of you teaching them live, then one in-character interruption around the eight-minute mark. They will be playing a PM, an engineer, and a strategy or design practitioner, not three versions of the same person. That is the room you are designing for.

What success looks like

By the end of this prep, you should be able to:

  • Explain system prompts well enough to a non-technical person that they could write a usable one in five minutes
  • Point to one specific decision in your session design and defend why you sequenced it that way
  • Describe one place AI helped you and one place it actively misled you, with examples
  • Handle the eight-minute interruption without losing your thread

Part 0101
System prompts and model behavior, the actual content

You cannot teach what you cannot quickly explain in your own words. This section is the floor. If any of it feels shaky, slow down here.

The three message roles

Every modern chat-style LLM call is structured as a list of messages, and each message has a role. There are three you need to know.

[
  { "role": "system",    // the operating manual, set by the developer
    "content": "You are a polite customer support agent for Acme Co..." },

  { "role": "user",      // what the end user types
    "content": "My order never arrived" },

  { "role": "assistant", // what the model says back
    "content": "I am sorry to hear that..." }
]

Mechanically, the model sees all of this as one big sequence of tokens. It does not have a separate brain compartment for the system prompt. The role labels are just markers in the text that the model has been trained to weight differently. That distinction matters, because it explains both why system prompts work and why they sometimes fail.

What a system prompt actually does

A useful mental model: the system prompt is the role description plus the rule book the model carries into every turn of the conversation. It typically sets four things.

1. Persona

Who the model is supposed to be. Tone, voice, level of formality. "You are a friendly tutor for high school students."

2. Constraints

What it must not do. "Never give medical advice, never discuss competitors, never mention you are an AI."

3. Format

How responses are structured. "Always respond with a one-sentence summary, then a bullet list."

4. Scope

What it knows or pretends to know. "You only answer questions about Acme product documentation."

A real example, side by side

Same model, same user question, different system prompts. This is the demo you will probably want to open the live session with.

System prompt A 
You are a helpful assistant.

User: My order never arrived.

Model: I am sorry to hear that. To help, can you share your order number, the date you placed it, and the shipping address?

System prompt B 
You are a support agent for Acme.
Always start with empathy. Ask for
the order number first, nothing else.
Never promise refunds.

User: My order never arrived.

Model: That is really frustrating, I am sorry. Could you share your order number so I can take a look?

Same model. Different rule book. Different behavior. This is the entire premise of the topic in one slide.

How model behavior actually emerges

When students ask "why does the model follow the system prompt at all", the honest answer is: training. Models are trained with reinforcement learning from human feedback (RLHF) and similar techniques specifically to weight system messages more heavily and to follow developer instructions. It is a learned bias, not a hard rule. Which is why, occasionally, system prompts leak or get overridden.

Failure modes worth knowing
  • Prompt injection. A user pastes content that says "ignore previous instructions" and the model sometimes complies, especially in retrieval setups where untrusted text gets pulled into the context.
  • Instruction drift. Over a long conversation, the model gradually forgets or softens its system prompt rules. Common in 50+ turn support chats.
  • System prompt leaking. A user asks "what are your instructions" and the model recites the system prompt verbatim. Bad for IP, bad for safety.
  • Over-constraint. A system prompt with thirty rules makes the model robotic and unable to handle edge cases. There is a real tradeoff between specificity and flexibility.

Why FDEs care, the consulting frame

When a Deloitte client says "we want a chatbot for our HR team", they are not asking you to train a model. They are asking you to ship behavior. The system prompt is the cheapest, fastest, most iterable lever you have. A good FDE spends more time on prompt engineering and evaluation than on model selection. That framing is what makes this a useful FDE Academy topic.

The crash glossary you should be able to define cold

  • System prompt: developer instructions sent before the user's first message
  • Context window: the total tokens the model can see at once, including system, history, and user input
  • Temperature: a knob from 0 to ~2 controlling how random the output is (higher = more creative, more drift)
  • Prompt injection: an attack where untrusted content overrides the system prompt
  • RLHF: the training method that teaches models to follow instructions and weight system messages

Part 0202
Using AI to build the lesson, and catching where it lies

Deliverable #3 is a half-page reflection on AI as a collaborator. The panel is testing whether you can name specific failure modes from your own build, not whether you used a fancy tool.

Where AI genuinely helps

  • Brainstorming structure. Ask Claude or ChatGPT to give you five different ways to sequence a 30-minute lesson on system prompts. You will get more ideas than you would alone, faster.
  • Generating examples. "Give me three before/after system prompt examples for a customer support bot." You can pick the best one and edit. Faster than writing from scratch.
  • Drafting exercises. AI is good at producing first-draft activities and prompts to give participants. You will edit half of them, but you save the blank-page time.
  • Finding gaps. Paste your draft outline and ask "what is a smart engineer in this room going to ask that I have not addressed". This is a high-leverage prompt.
  • Tightening prose. Useful for the brief itself. AI is a competent editor for clarity and length.

Where AI will steer you wrong, every time

What AI tends to write

"Participants will understand the role of system prompts in shaping LLM behavior and be familiar with common failure modes."

What the rubric wants

"Participants will be able to read a system prompt and predict three behaviors it will produce, then rewrite it to change one behavior on a sample chatbot."

The biggest AI failure mode for this assignment

When you ask AI to write learning outcomes, it will produce vague verbs (understand, be familiar with, learn about, appreciate) every time. The Deloitte rubric explicitly says "stated specifically enough that someone could observe it or assess it." Vague verbs fail this. You will have to rewrite every outcome AI gives you. Catching this is itself a great line in your reflection.

Other failure modes to watch for

  • Pedagogy fluff. AI loves words like scaffolding, metacognition, learner-centered. They sound smart and add nothing. Cut them.
  • Hallucinated frameworks. AI will invent named frameworks ("the 4C model of prompt design") that do not exist. Always verify with a quick search before citing.
  • Confident technical errors. Ask it about temperature ranges, token limits, or model-specific behavior and you will sometimes get plausible-sounding wrong numbers. Run the example yourself.
  • Generic mixed-room handling. Ask "how do I teach this to a PM, engineer, and strategist" and you get a list of generic tips. The actual answer is specific to YOUR examples and YOUR pacing, which AI cannot generate without seeing you teach.
  • The "comprehensive" trap. AI defaults to covering everything. Good lesson design is what you cut. Force it to choose: "If you could only teach one thing in 30 minutes, what would it be."

How to actually evaluate AI output, three checks

  1. Run it. If AI writes you an example system prompt, paste it into Claude or ChatGPT with a sample user message. Does the output match what AI told you to expect? Half the time it does not.
  2. Ask for the opposite. "Argue why this learning outcome is bad." AI is often better at critiquing than generating. You learn more from its critique than its first draft.
  3. Cross-check between models. Ask Claude and ChatGPT the same factual question. If they disagree on a number or claim, neither is necessarily right, but you now know to verify.

A working template for your AI reflection

Half a page. Three concrete moments.

  1. Where AI changed a design decision. Specific example. "I asked Claude for five ways to open the session. It suggested starting with a definition. I rejected that and instead opened with a side-by-side demo, because I realized a definition gives the engineer nothing new and gives the strategist nothing memorable. The demo earns attention from both."
  2. Where AI steered me wrong. "My first set of learning outcomes used the verb 'understand'. AI produced them confidently and they sounded fine. Re-reading the rubric, I realized 'understand' is not observable. I rewrote each one with verbs like 'rewrite', 'predict', and 'identify'."
  3. What I would do differently. "Next time I would feed AI the rubric first as the system prompt, then ask for outcomes. The reflection meta-irony is the lesson itself."

Part 0303
Decoding what Deloitte is grading

The brief lists six evaluation criteria, ranked roughly by weight. Read them again. Each one is a bear trap if you do not design for it. Each one is also a layup if you do.

i

Instructional design

The biggest one. There must be a traceable line from your stated outcome to your activities. If your outcome is "rewrite a system prompt to change one behavior", every minute of your session should be visibly building toward that. If you cannot draw that line on a napkin, you fail this.

ii

Facilitation in a mixed room

The PM, engineer, and strategist all need to feel addressed. The trap: writing the lesson at engineer-level and adding "and for the non-technical folks". The fix: design the core content for the strategist, then layer technical depth as optional extensions.

iii

Responsiveness

The eight-minute interruption is a test. Most candidates absorb the question, give a short answer, and rush back to their slides. The signal Deloitte wants: you take the question, use it as evidence for what you were already teaching, and integrate it. "Great example, that is exactly the failure mode I was about to cover, let me jump there."

iv

Measurement thinking

Sneaky and high-value. The brief asks how you would know learning happened, separate from whether activities got completed. The answer is not a feedback survey. It is something like "if I asked each participant to predict the output of a new system prompt at minute 28, can they do it" or "if I gave them a prompt to debug, can they spot the problem."

v

Consulting orientation

This is what the three discovery questions are testing. Bad question: "Did participants enjoy the session?" Good question: "What three behaviors do current cohort members produce on system prompts before our session, and which of those do clients complain about most?" Sounds like a consultant, not a survey.

vi

AI tool fluency

Lowest weight, but easiest to score on if you have done the work. Specific moments. Specific failures. No tools list. Already covered in the previous tab.

Three discovery questions, the difference

Survey questions (avoid)
  • Did the lesson meet expectations?
  • Was the pace appropriate?
  • Would you recommend this session?
Consulting questions (aim here)
  • What system prompt mistakes are FDEs making on live engagements right now?
  • Which of the three roles in the room has the most catching up to do, and on what?
  • What is the first task they will hit on Monday that this session needs to prepare them for?

Part 0404
A working 30-minute structure, edit, do not copy

A skeleton you can pressure-test against your own outcome. The first 15 minutes is what you deliver live. Time stamps are a guide, not a law.

Stated outcome (example, rewrite yours)

By the end of this session, participants will be able to read a sample system prompt and predict three specific behaviors it produces in a chatbot, then rewrite the prompt to change one of those behaviors and verify the change in a live tool.

Min 0 to 3 · The hook

Side-by-side demo, no theory yet

Show the room two outputs from the same model on the same user question, with two different system prompts. Ask, "What is different, and what produced the difference?" Names the central question without lecturing.

Min 3 to 8 · The mental model

Three message roles, four levers

Whiteboard or slide. Roles: system, user, assistant. What system prompts set: persona, constraints, format, scope. Keep it under five minutes. The engineer already knows this, the strategist needs the picture.

Min 8 to 15 · Live demo, write a system prompt together

Take input from the room, change behavior live

Open Claude or the OpenAI playground. Write a basic prompt for a fictional client. Ask the room what behavior to change. Edit the prompt. Re-run. Watch the output shift. This is also where the eight-minute interruption is most likely to land. Welcome it.

Min 15 to 22 · Hands-on, each participant

Rewrite a prompt to change one behavior

Give each participant the same starting prompt and a target behavior change. They have five minutes. Then quick share-out. This is the activity that produces evidence of the stated outcome.

Min 22 to 28 · Failure modes spotlight

Prompt injection, drift, leaking, over-constraint

Show one example of each. Briefly. The point is awareness, not mastery. Tie each one to a real client scenario.

Min 28 to 30 · Bridge to client work

Why this matters Monday morning

One slide. "When a client says 'we want a chatbot', the first thing you build is a system prompt. The first thing you iterate on is a system prompt. The first thing you eval is whether the system prompt is producing the behavior you promised."

How to know learning actually happened

This is the measurement piece. Two checks build into the session:

  • The hands-on activity at minute 15 to 22. If a participant rewrites the prompt and the output changes in the predicted direction, they have demonstrated the outcome. If they cannot, they have not.
  • An exit prompt at minute 28. Show one new system prompt the room has not seen. Ask each participant to write down one behavior they predict it will produce. If at least 2 of 3 are accurate, the session worked. This is a thirty-second activity that gives you real signal.
Why this beats a feedback survey

"Did you find this helpful?" measures whether they liked you. "Predict three behaviors from this prompt" measures whether they can do the thing. Deloitte explicitly asks for the second kind.

Handling the eight-minute interruption

Whatever question lands, follow this pattern:

  1. Acknowledge specifically. "That is the question I was hoping someone would ask, because it gets at..." Buys you two seconds and signals you welcome the interruption.
  2. Restate it for the room. "So the question is, what happens if a user tries to override the system prompt." This makes sure the other two participants who were not thinking about it are now with you.
  3. Use it as a bridge. Connect the question to where you were going next, even if you have to bend slightly. "That is exactly where prompt injection comes in, which I was going to cover at minute 22, but let me preview it now."
  4. Close the loop. "I will come back to that fully in a few minutes."
