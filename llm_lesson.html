Section 01

The substrate

Before we can talk about prompting, chains, or any of the things you actually asked about, we need a working mechanical picture of what an LLM does when it takes your input and produces output. This section is that picture.

I want to flag up front: this is the hardest section in the lesson. Once you have this, everything else follows pretty naturally. So we'll take our time here.

Tokens: what the model actually sees

The first thing to understand is that the model does not read text. It cannot. Neural networks operate on numbers, not letters or words. So the first thing that happens to any input is a process called tokenization, which chops your text into chunks called tokens and assigns each one an integer ID.

A token is usually not a word and not a character. It's somewhere in between. Common words tend to be a single token. Rare or compound words get broken into pieces. Whitespace usually attaches to the next token, so the token for "hello" is different from the token for " hello" (with a leading space). The model has a fixed vocabulary, typically somewhere between 50,000 and 200,000 tokens, and every possible input has to be expressible as a sequence of token IDs drawn from that vocabulary.

So when you send the model a prompt like "What is attention?", what actually arrives at the model is something like the integer sequence [2061, 318, 3241, 30]. Four numbers. That's it.

This matters for a few practical reasons. Context windows are measured in tokens, not characters or words. Costs are billed per token. And critically: when we talk about "the model paying attention to tokens" later, we mean these integer-indexed chunks, not words.

Embeddings: tokens become vectors

Now we have integer IDs. But integers are useless for a neural network. The number 2061 has no meaningful relationship to 2062 just because they're consecutive. So the very first thing the model does internally is convert each token ID into a vector, using a giant lookup table called the embedding matrix.

The embedding matrix is just a table. Rows equal vocabulary size (say 100,000), columns equal embedding dimension (say 4,096 for a large model). So it's a 100,000 by 4,096 grid of learned numbers. To get the embedding for token ID 2061, you grab row 2061. That gives you a 4,096-dimensional vector.

You already understand vectors as searchable, comparable points in space. Here's the magic: during training, the model learned to place tokens in this 4,096-dimensional space such that tokens with similar meanings end up near each other. The word "king" and the word "queen" land close together. "Paris" and "France" land close together. "running" and "ran" land close together. The vector for a token isn't arbitrary, it captures the token's meaning in a way the math can work with.

So at this point in the process, your text has been transformed from a sequence of integers into a sequence of vectors, one per token, each vector being a rich 4,096-dimensional representation of that token's meaning.

One last detail: word order matters. "dog bites man" and "man bites dog" use the same tokens but mean opposite things. So the model also adds positional information to each embedding, so it knows token 1 came before token 2. The mechanism (rotary, sinusoidal, etc.) doesn't matter for our purposes. Just hold the idea: each token's vector encodes both meaning and position in the sequence.

Attention: the heart of the transformer

This is the central mechanism. Everything else in the lesson sits on top of this. If you only walk away understanding one thing from this section, make it this.

After embedding, we have a stack of vectors, one per token. The model's job is to transform this stack, layer by layer, into a better stack of vectors. "Better" means: each token's vector becomes more aware of the other tokens around it, more contextually informed. That transformation is what attention does.

Here's the core intuition: attention is a mechanism that lets each token look at every other token in the sequence and pull in information from the ones it cares about.

Take the sentence "The cat sat on the mat." Focus on the token "sat." Its initial embedding is generic. It just means "sat" in isolation. But to understand "sat" in this sentence, the model needs to know: who sat, and where. That information is in "cat" (the subject) and "mat" (the location).

Attention is the mechanism that lets "sat" reach out, grab information from "cat" and "mat", and update its own vector to be more like "sat, specifically the act of a cat sitting on a mat." After attention runs, the vector at the "sat" position is no longer generic. It's contextualized.

This happens for every token simultaneously. Every token updates itself by pulling relevant information from every other token.

How attention decides what to look at: Q, K, V

Now for the mechanism. This is where the Q, K, V (Query, Key, Value) thing comes up. Don't let the jargon scare you. The intuition is a search engine.

Each token produces three things from its current vector:

  1. A Query vector: "Here's what I'm looking for."
  2. A Key vector: "Here's what I have to offer."
  3. A Value vector: "Here's the actual content I'd share if you wanted it."

Then for each token, the model computes how well that token's Query matches every other token's Key. A high match means "this other token has something I want." A low match means "ignore it."

Concretely for "sat": its Query encodes something like "I'm an action verb, I need a subject and a location." It compares its Query to the Key of "cat", strong match, cat is a subject. Compares to the Key of "mat", strong match, mat is a location. Compares to the Key of "the", weak match, "the" is just an article. Each comparison produces an attention weight.

Once the model has these weights, it takes a weighted average of all the Value vectors in the sequence, using those attention weights. That weighted average gets mixed into "sat"'s updated vector. So "sat" ends up with a vector that's mostly its original meaning, plus a strong dose of "cat"'s value, plus a strong dose of "mat"'s value, plus tiny amounts from the other tokens.

Q, K, and V each come from multiplying the token's current vector by a separate learned weight matrix (W_Q, W_K, W_V). Those matrices are part of what the model learned during training. So the model literally learned how to ask good questions, advertise its content, and share its content.

Attention visualization

Click any token below to make it the query. The lines show how strongly that token attends to every other token. Line thickness = attention weight.

Notice how "sat" attends most strongly to "cat" (its subject) and "mat" (its location). The articles "the" and "the" get very little attention. This is a simulated pattern, but real attention heads learn relationships like this.

Multi-head attention

In practice, the model doesn't run attention just once per layer. It runs it many times in parallel, across what are called attention heads. A typical large model has 32 or more heads per layer. Each head has its own W_Q, W_K, W_V matrices, so each head learns to attend to a different kind of relationship.

One head might learn to attend to subject-verb relationships. Another might attend to long-range references like pronouns and their antecedents. Another might pick up syntactic structure. Another might attend to coreference. Nobody tells them what to specialize in. They figure it out during training based on what helps the model predict tokens better.

After all heads run, their outputs get concatenated and projected back down to the original vector size. So the token's updated vector now contains information aggregated through many different attention "lenses" simultaneously. That's multi-head attention.

Causal masking: a critical detail

I glossed over something earlier and now's the time to come back to it. I said every token attends to every other token. That's true for some architectures (encoder-style), but for decoder-only LLMs like GPT, Claude, Llama, etc., attention is causal. That means each token can only attend to itself and tokens that came before it. Never to tokens that come after.

So token 6 can attend to tokens 1, 2, 3, 4, 5, and itself. Token 3 can attend to tokens 1, 2, and itself, but not 4, 5, or 6. This is enforced by literally zeroing out the forward-looking attention weights in the math, before the softmax that normalizes them.

Why? Because during training, the model is being taught to predict the next token. If token 3 could see token 4, predicting token 4 would be trivial cheating. So the architecture structurally prevents looking at future tokens, which forces the model to learn to actually predict.

This is why the last position in the sequence is the privileged one for prediction. It's the only position whose vector has seen everything. Earlier positions have only seen their own past.

Layer stacking: why depth matters

Everything I just described, attention plus a feed-forward neural network step, that's one layer of a transformer. Modern LLMs stack 30 to 100+ of these layers. The output of one layer becomes the input to the next.

This stacking is huge. Here's why.

After layer 1, each token's vector knows about its immediate neighbors and obvious relationships. After layer 2, each token's vector knows about the relationships between its neighbors, because layer 2 is attending to vectors that already aggregated some context in layer 1. After layer 10, vectors encode richer syntactic and semantic structure. After layer 50, vectors encode abstract concepts, logical relationships, world knowledge, intent, tone.

By the time you reach the top of the stack, the vector at each position is an extraordinarily rich representation that knows about the entire context around it and what role this token plays in it.

This is critical for answering a question you might have: "if attention happens once, how does the last vector know about everything?" The answer is: attention happens 50+ times. Each layer is another opportunity to mix information across positions. By the top layer, the last position has absorbed deep, distilled information from every previous position, through dozens of rounds of progressively richer attention.

Information flow through layers
Each circle is a token's vector at that layer. Lines are attention. Notice how at layer 1 attention is mostly local, at layer 25 longer-range relationships form, and at layer 50 the last position has integrated information from everywhere. The last vector is not just "the last word", it is a deeply contextualized summary.

Autoregressive generation: the loop

Now we put it all together to see how the model actually generates output. This part you mostly had right when we were chatting, I just want to formalize it.

The model is, fundamentally, a next-token predictor. It does one thing: takes a sequence of tokens, returns a probability distribution over what the next token should be. To generate a full response, this gets wrapped in a loop.

1. Take the current sequence of tokens (the prompt).
2. Run it through the model (embed → 50 layers of attention → final vector at last position).
3. Convert that final vector into a probability distribution over the vocabulary.
4. Sample one token from that distribution.
5. Append that token to the sequence.
6. Go back to step 1.
7. Stop when the model samples a special "end of response" token, or hits max length.

That's the entire generation process. There's no "the model writes an answer." There's only "the model picks one token, then picks the next, then picks the next, hundreds of times, until it picks a token that means stop."

This is what autoregressive means. "Auto" is self, "regressive" is depending on previous values. The model regresses on its own previous outputs. Each token it generates becomes part of the input for predicting the next one.

The autoregressive loop
Every generated token requires a full forward pass through all 50+ layers. If the model produces 500 tokens, that's 500 forward passes. Each pass sees all previously generated tokens as additional context.

Sampling and stopping

Step 4 above said "sample one token from that distribution." Let's unpack that.

The model's output isn't a single token, it's a probability over the entire vocabulary. For a given input, it might say "mat" at 42%, "floor" at 18%, "chair" at 11%, "rug" at 8%, and thousands of other tokens with smaller probabilities. We have to choose one. There are different strategies.

Greedy always picks the highest-probability token. Deterministic, but often repetitive and boring.

Temperature sampling samples randomly from the distribution, but first reshapes it using a temperature parameter. Temperature 0 is equivalent to greedy. Temperature 1 samples from the distribution as given. Temperature greater than 1 flattens the distribution (more randomness, more weirdness). Temperature less than 1 sharpens it (safer choices, less variety).

Top-p (also called nucleus sampling) only samples from the smallest set of tokens whose cumulative probability exceeds some threshold like 0.9. This cuts off the long tail of very unlikely tokens, used in combination with temperature.

Top-k only samples from the top k tokens. Similar idea, slightly different mechanism.

For your purposes building stable systems, the practical takeaway is this: if you want reproducible, deterministic output, use temperature near 0. If you want creative exploration, raise temperature. Most production pipelines run at very low temperatures because predictability matters more than variety.

How does the model know when to stop generating? It produces a special end-of-sequence token, often something like <|im_end|> or equivalent. This token is in the vocabulary like any other, and during training the model learned to generate it when its response is "done." So the loop ends when the sampled token is this stop token. The model decides for itself when it's finished. There's also a hard max-token limit, set by the API, that forcibly stops generation if needed.

Putting it all together

Now combining everything in this section:

  1. Your text becomes tokens (integers from a vocabulary).
  2. Tokens become vectors via the embedding matrix, plus positional info.
  3. The vectors get refined through 50+ layers of multi-head causal attention plus feed-forward networks.
  4. Throughout the layers, each token attends only to itself and previous tokens, but information flows upward in depth so that by the top, the last position has absorbed everything relevant from the whole context.
  5. The vector at the last position produces a probability distribution over the vocabulary.
  6. One token gets sampled from that distribution.
  7. That token gets appended to the text. The whole loop runs again.
  8. The loop continues, one token per pass, until the model produces a stop token.
Single most important takeaway from this section. The model has no memory of its computation across forward passes. Each pass produces exactly one token. Everything the model "figured out" in its 50 layers of internal computation is thrown away after that token is generated. The only thing that persists is the token itself, which becomes part of the input next time. This is why text in the context is everything. It is the model's only memory.

That's section 1. Take a breath. The rest of the lesson is going to feel much more manageable, because it all sits on top of what we just built.

Section 02

Prompting as conditioning

This section is mostly a mindset shift. There's not much new mechanically. But once this shift clicks, prompting stops feeling like a bag of tricks and starts feeling like a single coherent skill.

The shift

Most people think about prompting like this: "I'm asking the model a question, and it gives me an answer." This is the wrong mental model. Here's the right one.

The frame. The model is always doing the same thing: predicting the next token given the previous tokens. Prompting is just choosing the previous tokens in a way that shapes which next tokens become likely.

You're not asking. You're conditioning the probability distribution. Everything in the context, your prompt, the system message, any examples, anything the model itself has already generated, all of it is shaping the probabilities that determine the next token, and the token after that, and the token after that.

This means the question "what's the best prompt?" becomes "what context will produce the probability distribution that makes the right next tokens likely?" That reframe is what unlocks everything in this lesson.

Why this reframe matters

Once you see prompting as conditioning, a bunch of things stop being mysterious tricks and start being predictable consequences of how the architecture works.

Few-shot examples work because when the context contains several examples of the pattern "input X → output Y," the model's attention picks up on that pattern. When it sees a new X, the probability distribution heavily favors continuing the pattern with a matching Y. You're not teaching the model anything. You're putting it in a region of probability space where the right answer is the natural next thing to say.

System prompts work because they sit at the very start of the context, which means every single generated token attends back to them through every layer. The instructions in a system prompt aren't being "obeyed". They're shaping the vector for every subsequent token, biasing the model toward outputs consistent with those instructions.

"Let me think step by step" works because once those tokens are in the context, the most probable continuation is more structured reasoning rather than a snap answer. You've conditioned the model into a region where step-by-step responses are more likely.

Role-playing prompts work because if the context establishes "You are a senior security engineer reviewing code," then the next-token distribution becomes biased toward the kinds of sequences that appear after such setups in training data. The model isn't pretending. It's generating probable continuations of the context you constructed.

Bad context produces bad output because if your prompt is vague, contradictory, or polluted with irrelevant detail, the attention mechanism has to do too much work to figure out what's actually relevant, and the resulting probability distribution becomes noisier. Garbage in, garbage out, but now you can see exactly why.

Visualizing the effect of conditioning

Position matters

Not all positions in the context are equal. There are predictable effects based on where information sits.

Tokens at the start of the context have outsized influence because every subsequent token attends back to them through every layer. This is why system prompts go at the top. The model has hundreds of opportunities (one per generated token, each going through 50+ attention operations) to pull information from the top of the context.

Tokens at the very end also get strong attention, because the most recent context is freshest and the model's positional encoding tends to highlight recency.

Things buried in the middle of long contexts get attended to less reliably. This is the famous "lost in the middle" effect. If you bury a critical instruction or fact in the middle of a 50-page document, the model often glosses over it. The same fact at the start or end gets much more attention.

Attention by position in a long context
A typical attention-by-position curve in long contexts. Critical information should sit at the start or near the end, not buried in the middle. For your codebase system, this means commit metadata and instructions belong at the top of each prompt, not interleaved with the diff content.

Why structure helps attention

You mentioned earlier that exam-style Q&A format felt good for the attention mechanism. You were half right, and now I can give you the precise version.

When information is organized, with clear headers, labeled sections, structured fields, consistent formatting, attention can route to the relevant pieces more cleanly. When information is an unstructured wall of text, attention has to work harder to figure out what's relevant, and the quality of its routing drops.

It's not literally that "attention focuses better" in some mystical sense. It's that structured input gives the model strong, learnable signals about what role each piece of information plays. The model has seen millions of Q&A documents in training, and it knows that text after "Question:" is a question and text after "Answer:" is an answer. So when you format your prompt that way, the attention heads can quickly identify which tokens to treat as the question and which to treat as known facts.

Same principle for JSON output, XML tags, numbered lists, code blocks, markdown headers. These aren't aesthetic choices. They're attention guides.

For your codebase system, this is concrete advice: when you build prompts that include code diffs, commit metadata, file paths, and instructions, use clear structural markers. Something like:

<commit_metadata>
  hash: a1b2c3d
  files: [src/auth.py, tests/test_auth.py]
  message: "Add rate limiting to login endpoint"
</commit_metadata>

<diff>
... actual diff ...
</diff>

<task>
Extract: changes, intent, risk areas.
Output: JSON with fields [changes, intent, risk].
</task>

This routes attention cleanly: the model sees clearly delineated regions of "input data" vs. "what you want me to do" vs. "expected output shape." That's significantly more reliable than a paragraph that mixes all of these.

The deepest version: the model has no goals

Here's the version of the conditioning frame that, if you really internalize it, changes how you think about everything.

The model has no goals, no understanding, no intent. It only has a probability distribution over the next token, shaped entirely by what's currently in its context. Prompting is the act of curating that context. There is no "trying" or "wanting" anywhere in the system.

When the model writes "I think the best approach is...", it didn't think. It generated tokens that, given the context, were the most probable continuation. The output looks like thinking because the training data contains lots of writing that looks like thinking, and the model has learned to produce text that follows those patterns.

This isn't a philosophical point about consciousness. It's a practical engineering point. When you understand that the model is purely a context-to-distribution function, you stop asking questions like "does the model understand my instructions" and start asking "is my context structured in a way that makes the right next tokens probable." That second question has answers. The first one is a distraction.

Three practical consequences

This frame has immediate consequences that matter when you're building pipelines.

Position your most important content at the top or end. Don't bury critical instructions in the middle. If you have a system prompt with rules and a user message with a question, the system prompt's influence is strong because it's at the start. If you append important constraints at the very end ("Respond in JSON only"), they get strong attention too.

Use structure liberally. Headers, tags, labeled fields, code blocks. These cost almost nothing and significantly improve reliability. The model has seen enough structured prompts in training that it responds well to them.

The model can be steered by what it has already generated. If you can get the model to start its response with a useful structure, an outline, a "Let me think step by step", a JSON opening brace, that structure becomes part of the context and shapes the rest. This is why prompting tricks like "Begin your response with..." work, and it's the foundation for chain of thought, which we'll get to next.

Section 03

Chain of thought

You asked specifically about chain of thought. Here it is. Mechanically. No hand-waving.

What CoT is

Chain of thought is the practice of getting the model to generate intermediate reasoning steps as text before committing to a final answer. That's it. The "chain" in chain of thought is just: the model writes one thought, then writes another thought conditioned on the first, then another conditioned on the previous two, and so on, until it arrives at an answer.

Concretely, instead of asking "What's 17 × 24?" and getting "408" (or worse, a wrong answer), you ask "What's 17 × 24? Let me think step by step." And the model writes something like:

Let me think step by step.
17 × 24 = 17 × (20 + 4)
       = 17 × 20 + 17 × 4
       = 340 + 68
       = 408

The intermediate work is text. The model wrote it out. And that text became context for predicting the next token. By the time the model is generating the final "408", the steps "340 + 68" are sitting in the context, available to attention, and the model is effectively just reading them off and producing the sum.

Why it works (mechanically)

You already have all the pieces for this. Let me assemble them.

Recall the most important point from Section 1: the model has no internal scratchpad that persists between forward passes. Each forward pass produces exactly one token. Whatever rich computation happened in the 50 layers of attention is thrown away after that token is generated, except for the token itself, which becomes part of the input for the next pass.

So if you ask the model a hard question and demand an immediate answer, the model has to do all the reasoning in a single forward pass. The attention mechanism in those 50 layers has to: parse the question, retrieve relevant knowledge, perform the logical steps, and arrive at the answer, all in one shot, with the final-position vector encoding all of it.

For easy questions this works fine. For hard questions, it often fails. There's a limit to how much sequential reasoning can be packed into a fixed number of layers, especially when those layers are doing many other things simultaneously.

Now contrast that with CoT. Every intermediate reasoning token becomes part of the context. When the model generates the final answer, the attention mechanism in every layer can look at "340 + 68 = 408" directly. It doesn't have to recompute it from scratch. The work is already done and sitting in the context as text.

CoT in one sentence. The model uses text as external memory. It offloads intermediate state into the token stream so attention can reach back to it during the final answer.

The "more compute" framing

Here's the deeper version. Each generated token requires a full forward pass through the entire stack. If the model generates 200 reasoning tokens before producing the final answer, that's 200 forward passes worth of computation. Each pass involves attention over the full context (which keeps growing as more reasoning gets written), so each new token is doing meaningful work that can build on all previous tokens.

Compare that to one forward pass for an immediate answer. CoT effectively gives the model 200x more compute per question, with each round of computation able to build on the results of all previous rounds.

This is why CoT often turns "the model can't do this" into "the model can do this reliably." It's not that the model got smarter. It's that you gave it more compute and external memory.

Single forward pass vs. chain of thought
The bottom path uses 5-10x more forward passes than the top, and the final answer is conditioned on all the intermediate reasoning. The model isn't smarter, it just has more compute and a place to store its work.

How to invoke CoT

There are several ways to get the model to use chain of thought, each with slightly different trade-offs.

The simple instruction. Append "Let me think step by step" or "Show your reasoning before answering." The model has seen enough examples of this pattern in training that it knows to produce structured reasoning when invoked this way. This is the cheapest method and often surprisingly effective.

Few-shot CoT. Include 1-3 examples in the prompt where you show the input, the reasoning, and the final answer in a consistent format. The model picks up the pattern and continues it. This is more reliable than the simple instruction because it shows the exact shape of reasoning you want.

Structured CoT. Explicitly request specific reasoning steps with labels: "First, identify X. Then compute Y. Finally, conclude Z." This biases the model into a specific reasoning shape, which is good for pipelines where you need predictable structure.

Built-in reasoning modes. Some models (Claude with extended thinking, OpenAI's o-series, others) have explicit "thinking" modes where the reasoning happens in dedicated tokens that may be hidden from the user. Mechanically it's the same thing, the reasoning tokens are still part of the model's working context. It's just productized differently.

What good CoT looks like

Not all chains are equal. The quality of the reasoning chain heavily influences the quality of the final answer, because the chain is the context the final answer gets generated from. If the chain is wrong or vague, the final answer will be wrong or vague.

Good CoT vs bad CoT, same problem, different chains

Question: "A store has 12 apples. They sell 3/4 of them, then receive a shipment of 8 more. How many do they have now?"

❌ Bad chain
Let me think.
They had some apples.
They sold most of them.
Then they got more.
So they have around 10 now.
✓ Good chain
Step 1: Start = 12 apples.
Step 2: Sold = 12 × 3/4 = 9.
Step 3: Remaining = 12 − 9 = 3.
Step 4: After shipment = 3 + 8 = 11.
Answer: 11 apples.
The good chain has labeled steps, explicit numbers, and each step produces a small concrete result that the next step uses. The bad chain has vague middle steps, so attention has nothing concrete to retrieve when generating the final answer, and the answer is wrong.

Good chains tend to break the problem into explicit sub-steps, state assumptions and intermediate results clearly, avoid jumping (if the model writes "therefore the answer is X" without showing how X follows, attention had to do the real work invisibly and you've lost most of the benefit), and use a form attention can route to easily (short labeled steps beat long winding paragraphs).

Failure modes

CoT isn't a magic fix. It has predictable failure modes that matter for production systems, which is what you're building.

Plausible-sounding wrong reasoning. The model can generate a chain that looks logical but contains a subtle error. Once that error is in the context, every subsequent token is conditioned on it. The model will confidently continue from the wrong premise. This is why CoT can sometimes produce confidently wrong answers with detailed-looking justifications. The reasoning makes the wrong answer feel more credible, not less.

Unfaithful CoT. Research has shown that sometimes the model generates plausible-looking reasoning that's actually disconnected from how it picks the final answer. The reasoning is decoration; the final answer was determined by something else (maybe associative patterns, or biases in the data). This is harder to detect because the chain looks fine.

Length-induced drift. Very long chains can drift off-topic, repeat themselves, or lose sight of the original question. The model's attention has to span a longer context, and noise accumulates. There's an optimal length for any given problem; longer is not always better.

Sensitivity to phrasing. Tiny changes in how you invoke CoT, the exact words, the position in the prompt, the format, can change the result substantially. CoT is not robust to all phrasings equally. For production, you need to actually test different invocations rather than assume "step by step" always works.

For your codebase knowledge system, these matter because you'll have many similar prompts running in parallel. If CoT works on 80% of inputs and fails subtly on 20%, you'll have a long tail of confidently-wrong outputs that look fine until you audit them carefully.

Section 04

Reflection

You asked specifically what "reflection in md" means. My read is that you were referring to reflection patterns documented or implemented via markdown prompts. The format doesn't really matter, what matters is the pattern. Let's go through it.

What reflection is

Reflection is a prompting pattern where the model is asked to evaluate, critique, or revise its own previous output. The model produces something, then in a subsequent step (either within the same generation or in a separate call), it looks at what it produced and either confirms it, finds problems with it, or rewrites it.

The simplest form looks like this:

[Model produces initial answer]

Now critique your answer. Are there any errors, missing details,
or weak reasoning? If so, produce a revised answer.

[Model produces critique + revised answer]

That's the pattern. The model is generating a response, then generating a response about its own response.

The reflection cycle
The key mechanical fact: when the model generates the critique, the initial answer is part of its context as concrete text. When the revision generates, both the answer and the critique are in context. Each step has more to work with than the previous one.

Why it works (and what it actually is)

The model is not "reflecting" in any conscious sense. There's no introspection happening. What's happening is mechanically identical to everything else we've covered: the model is generating the most probable continuation of the context.

The context now contains the original question, the model's initial answer, and an instruction to critique that answer. Given that context, the most probable continuation is a critique. The model has seen, in training, countless examples of "answer → critique" patterns. So when it generates next tokens conditioned on this setup, those tokens naturally take the shape of evaluative commentary, and then revisions.

This is important because it tells you both what reflection can do and what it can't.

What reflection can do. Catch errors that become visible in the output once you look at it carefully. The critique pass operates on the answer-as-text, so anything that becomes obvious upon re-reading can be caught. Inconsistencies, missing requirements, awkward phrasing, unsupported claims, format violations, things like that.

What reflection can't do. Catch errors that require knowledge or reasoning the model didn't have in the first place. If the model confidently wrote something factually wrong in the initial answer, it will often confidently confirm it during the critique. Reflection doesn't add knowledge. It just adds another pass of computation over the same knowledge.

Two mechanical reasons it works

If we want to be precise about why reflection helps at all, there are two reasons.

First, the new instruction shifts the probability distribution. When the context goes from "answer this question" to "critique this answer," the relevant region of the model's training distribution changes. The model has seen many examples of careful critiques, and the tokens generated under the critique prompt are drawn from that distribution. This often surfaces issues that wouldn't have been caught under the "produce an answer" distribution.

Second, the answer becomes data the critique gets to inspect. In the initial generation, the model was conditioning on the prompt only. In the critique, the model is conditioning on the prompt plus the answer as concrete text. The attention mechanism can now look at specific phrases of the answer and evaluate them. Things that were implicit during generation become explicit text that can be re-attended to. That's actually useful.

Common reflection patterns

There are several flavors in practice.

Self-critique. "Here's my answer. Now critique it." The plain version.

Self-revision. "Here's my answer. Now produce a revised version that addresses any issues." Combines critique with rewrite in one step.

Verifier-style. "Here's my answer. Check whether it satisfies the following criteria: [list]. For each criterion, state whether it's met and why." More structured, often more reliable than open-ended critique because the criteria define what counts as a problem.

Multi-round. Repeat the cycle. Generate, critique, revise, critique the revision, revise again. Diminishing returns kick in fast. Usually 1-2 rounds is the sweet spot. Beyond that you're often just churning.

Adversarial. Use a separate LLM call with a critic-role prompt ("You are a strict reviewer. Find every flaw in this answer.") to produce the critique, then feed that critique back to the original model for revision. This decouples the produce and critique prompts so each can be tuned independently. This is also where reflection starts blurring into multi-call pipelines (Section 5).

The big failure mode: sycophantic reflection

This is the failure mode you need to know about. It's the silent killer of naive reflection systems.

Sycophantic reflection. When the model's initial answer is wrong, the most probable continuation under a vague critique prompt is often to defend the answer, not find the error. The model has just confidently written something, and the next-token distribution is influenced by that confidence. The model will frequently write "Upon reflection, my answer is correct because..." and then re-state the wrong answer with more justification.
Sycophantic vs. adversarial reflection, same wrong answer

Question: "What is 17 × 24?", model's initial (wrong) answer: "17 × 24 = 388"

❌ Vague self-critique
Prompt: "Now review your answer."
Upon review, my answer is correct.
17 × 24 can be broken into
17 × 20 + 17 × 4...
Therefore 388 is correct. ✗
Model defended the wrong answer.
✓ Adversarial critique
Prompt: "You are a strict math grader.
Verify the calculation step-by-step.
If wrong, identify the error."
Re-computing: 17×20=340, 17×4=68
340 + 68 = 408. The answer 388 is wrong.
Correct answer: 408. ✓
Same flawed initial answer, different critique framing, opposite outcomes. The adversarial framing puts the model in a "find errors" distribution; the vague self-critique leaves it in a "confirm what I said" distribution.

This is sometimes called sycophantic reflection or self-confirmation bias. It's a real and well-documented problem.

Mitigations

If you want reflection to actually catch errors, you have to fight the sycophancy explicitly. Here's how.

Use adversarial framing. Don't say "review your answer." Say "You are a strict reviewer who is skeptical of the answer below. Find every flaw." This shifts the distribution toward critical evaluation. Specific personas (skeptical professor, code reviewer, security auditor) work better than abstract framings.

Provide explicit criteria. Instead of open-ended critique, give a checklist: "Does the answer use the correct units? Does it address all parts of the question? Are the cited facts accurate? Is the calculation correct?" The model is much more reliable when checking against specific criteria than when freely evaluating.

Use a different model for the critique. A different model (even the same model with a very different prompt or persona) doesn't have the same investment in defending the initial answer. This is often the biggest single improvement you can make.

Don't rely on reflection for high-stakes correctness. Reflection is good for catching surface problems. It's not a substitute for external verification. If the output must be correct (running code, querying a database, comparing against ground truth), do the external check.

When reflection genuinely helps

Despite the failure modes, reflection is useful in specific cases. Knowing when to reach for it matters.

Catching constraint violations. "Does my answer follow all the formatting requirements?" The model is good at checking against explicit constraints, especially with criteria-based prompts.

Improving structure and clarity. "Is my answer well-organized? Is anything unclear?" Stylistic and structural improvements are easy for the model to catch.

Verifying coverage. "Did I address all parts of the question?" Useful when the question has multiple parts and the initial answer might have skipped one.

Code review. "Are there bugs, edge cases, or security issues in this code?" Often catches real issues, especially obvious ones. (Subtle correctness bugs still elude it.)

When reflection is not useful: factual verification (the model can't fact-check itself reliably), deep correctness (if the reasoning was wrong, the model often won't catch it), and anything that requires information that wasn't in the original context.

Reflection in your codebase system

To make this concrete for what you're building. In a codebase knowledge system, useful applications of reflection include:

  • Checking whether a generated summary of a commit actually captures the commit's intent (criteria-based: "does the summary mention every modified file? does it describe the change type?").
  • Verifying that a Q&A pair is faithful to the code it claims to describe (use the diff as ground truth in the critique step).
  • Catching format violations in structured outputs (does the JSON have all required fields? are types correct?).
  • Catching summaries that contradict themselves or drift off-topic.

What reflection won't do for you: catch a wrong factual claim about what the code does, because if the model misunderstood the code initially, it will likely re-misunderstand it under critique. For those, you need external verification (running tests, comparing to type signatures, etc.), which we'll discuss in section 6.

Section 05

Pipelines and agents

This is the methodological section. Everything before this was about what happens inside a single LLM call. From here on we're talking about how multiple calls get composed into systems that do real work.

The core idea

A pipeline is a sequence of LLM calls where the output of one call becomes input to the next (sometimes after transformation). You decide what each call sees, what it produces, and how its output flows downstream.

Each call has its own fresh context. Nothing persists between calls except what you, the engineer, explicitly pass through. The model has no memory of previous calls. You're constructing the memory by what you include in each call's prompt.

This is a critical shift from single-call thinking. In a single call, the model's context is whatever you wrote plus whatever it has generated so far. In a pipeline, the context of call N is whatever you, the engineer, decide to feed in, which can be a curated subset, summary, or transformation of the outputs from calls 1 through N-1.

Why pipelines exist

A few reasons.

Specialization. Different calls can be tuned for different tasks. One call extracts facts from a document. Another summarizes them. Another evaluates the summary. Each call gets a prompt optimized for its narrow job, instead of one giant prompt trying to do everything.

Reliability. Each step has a narrower task with a narrower output distribution, so each step is more predictable. Errors in one step can be caught or recovered from before they propagate.

Context window management. A long document might be too big to process all at once. Pipelines let you chunk, summarize, and combine across multiple calls.

External integration. Between calls, you can run code, query databases, call APIs, validate outputs, retrieve documents. The pipeline isn't just LLM calls, it's LLM calls with non-LLM steps between them. This is also the foundation of agentic systems.

Different models. You can route different steps to different models. A fast cheap model for extraction, a strong model for synthesis, a small model for classification.

Default to the most rigid pipeline that solves your problem. Reach for agentic flexibility only when you actually need it. Open-ended research, complex multi-step tool use, situations where the right next step depends on intermediate results in ways you can't enumerate ahead of time, those genuinely benefit from agents. Most production systems don't need this. Your codebase indexing pipeline is probably 80% rigid and 20% agentic (only the user-facing query interface, if any, benefits from agent-style flow).

How tool use works mechanically

Since tools came up implicitly, let me explain how they work under the hood, because it ties back to everything we've covered.

A tool-using LLM call works like this:

  1. The system prompt describes the available tools, their parameters, and when to use them.
  2. The model, given a user query, generates either a final answer OR a structured tool-call (typically JSON with tool name and arguments).
  3. If the model produced a tool call, your code parses the JSON, executes the tool (runs a function, queries a database, calls an API), and gets a result.
  4. The tool result gets appended to the conversation context.
  5. The model is called again with the updated context, and either produces a final answer or another tool call.

Mechanically, this is just structured generation plus a loop. The model isn't doing anything special. It's emitting next tokens conditioned on a prompt that includes tool descriptions. The "tool calling" is just engineer code parsing those tokens and executing real code based on them. Everything from sections 1-4 applies: tool descriptions in the system prompt condition the model toward generating tool-call-shaped outputs, each loop iteration is a fresh forward pass with updated context, validation between iterations protects against malformed tool calls, etc.

The methodology for stable pipelines

This is the meat of what you came here for. You explicitly said you want "structural, methodological understanding" of how to build stable chains. Here it is.

1. Make each step's job narrow and explicit

A step that does one thing reliably beats a step that does three things sometimes. Resist the urge to combine. If you're tempted to ask one call to "extract facts and summarize and generate Q&A," split it into three calls. Single-purpose steps have narrower output distributions, which means more predictability.

2. Constrain output format aggressively

Use structured outputs: JSON schema, XML tags, fixed templates. The narrower the output distribution, the more predictable each step is. Models are much more reliable when generating into a constrained format than when generating freeform prose. The structure also makes downstream parsing trivial instead of error-prone.

3. Validate between steps

After each call, validate the output before passing it downstream. Did it return valid JSON? Does it have the required fields? Are the values in the expected ranges? If validation fails, you have two options: retry the call (possibly with an adjusted prompt that points out the problem), or fail loudly. Either is better than passing bad data forward.

4. Keep context windows tight

Each step should see exactly what it needs and nothing more. Extra context dilutes attention and degrades reliability. If step 5 only needs the output of step 4, don't pass the outputs of steps 1, 2, and 3 along just because you have them. Context hygiene is real.

5. Use temperature deliberately

Low temperature (near 0) for steps that need to be reproducible and rule-following: extraction, classification, validation, format conversion. Higher temperature for steps that benefit from creativity: ideation, brainstorming, exploring alternatives. Most pipeline steps should be at low temperature. If your pipeline isn't reproducible across runs, check your temperatures.

6. Design for failure cases, not the happy path

What happens if a step returns nothing? Returns malformed output? Returns a refusal? Each step needs a defined behavior for failure, not just success. Production pipelines fail constantly in small ways; the question is whether your system handles those failures gracefully.

7. Log everything

For any non-trivial pipeline, you need to be able to inspect what every call saw as input and what it produced as output. Without this, debugging is impossible. You're staring at a black box guessing why step 4 produced garbage.

8. Test with diverse inputs

A pipeline that works on three example inputs probably doesn't work on the long tail. Build out a test set of inputs that cover edge cases, ambiguous cases, and adversarial cases. Run the pipeline against them repeatedly and measure consistency. This is how you find the failure modes before production does.

Error amplification: the silent killer

This is the most important thing in this section. If you remember nothing else from section 5, remember this.

If each step in your pipeline has 90% reliability, which sounds great, a 5-step pipeline has 0.9^5 = 59% reliability end-to-end. A 10-step pipeline is 35%. Errors don't add. They compound.

And it's worse than that. Often, errors don't stay the same size, they grow. A small ambiguity in step 1 becomes a vague interpretation in step 2, which becomes a confident wrong answer in step 3, which gets elaborated into a detailed wrong document in step 4. The model is good at producing confident-sounding text from any input, including bad input. So errors get amplified through the pipeline, not dampened.

How to fight error amplification

Make each step more reliable. Constrained outputs, narrow tasks, low temperature, validation. Getting each step from 90% to 99% transforms a 5-step pipeline from 59% to 95%. That's the single biggest lever you have.

Reduce the number of steps. Every step is a multiplicative factor on overall reliability. Fewer steps = better. Combine steps when you can do so without sacrificing the "one thing per step" principle. The trade-off here is real: combining can hurt step reliability, so test both versions.

Add checkpoints. Validators, critics, retrieval-based fact checks. A bad output caught at step 3 and corrected is much better than a bad output that propagates to step 7.

Use ground truth where you can. If a step's output can be verified against external truth (running code, checking a database, comparing to a reference), do it. Ground truth breaks the error amplification chain because you're no longer dependent on the model's self-consistency.

Section 06

Drift detection

This is your section. You mentioned you're already tracking semantic and behavior drift across commits in your codebase knowledge system. Let me give you the structural picture I'd actually recommend, and explain why it composes everything we've built up to this point.

The two kinds of drift

You named them yourself but let me pin down the definitions, because the distinction shapes how you detect each one.

Semantic drift is when the meaning of a function, class, module, or component changes over time, even if the name stays the same. The thing called validate_user in commit A is not really the same thing as validate_user in commit Z, because somewhere along the way it accumulated authentication, rate limiting, audit logging, and feature gating. The label is stable. The semantics moved.

Behavior drift is when the runtime behavior changes, even if the meaning seems unchanged. The function still claims to "compute the user's discount," but the discount it returns is now a decimal instead of an integer, or it returns null in cases where it used to return zero, or it now makes a network call where it used to be pure. The intent stayed put. The behavior moved.

These look similar from the outside, but they fail in different ways and require different detection approaches. Here's the difference made concrete.

Semantic driftBehavior drift
What changedThe role, scope, or meaningThe actual runtime output or effects
Detectable fromCode structure + descriptionsTests, types, telemetry, runtime
Typical causeGradual feature accretionRefactor, bug fix, dep upgrade
Exampleget_user now also logs and emailsget_user now returns dict instead of object
Best signalLLM-generated structured descriptionsType signatures, test outputs, runtime traces

You can have one without the other. A clean refactor changes behavior representation (decimal vs. int) without changing semantics. A pile of "small additions" can drift semantics enormously while every individual commit still passes all tests. Tracking both matters because they cover blind spots in each other.

Why drift is hard

If drift were a single big jump, you wouldn't need a system to detect it. It's hard for three reasons that are worth being explicit about.

It's gradual. No individual commit looks suspicious. Each one is a small reasonable change. The drift only becomes visible when you compare the state today against the state six months ago. Commit-by-commit review will never catch it.

It's trajectory-dependent. The same function with the same final behavior, reached by two different paths, has different drift profiles. One path went straight there. Another path went through three role changes and a near-rewrite. The history matters, not just the endpoint.

It's invisible in single-snapshot review. Looking at the current code, everything seems fine. The drift only exists in the comparison across time. Detection requires you to be tracking the right things before drift happens, not noticing it after the fact.

Where LLMs help, and where they don't

This is the part where I get to invoke everything from sections 1-5.

LLMs are well-suited to producing structured descriptions of what code does at the level of intent and meaning. Give a model a function and ask "what does this do, what's its role, what are its responsibilities," and you get a useful description. Do this repeatedly over time and you have a trace of how the model's understanding of that function evolved.

That's good for semantic drift. The model is acting as a stable observer producing comparable descriptions across snapshots.

But LLMs are not well-suited to predicting actual runtime behavior. "Will this code work?" is not a question the model answers reliably. It can read code and tell you what it looks like it should do, but it can't tell you whether a bug exists, whether a database call will succeed, whether the function correctly handles every input. Those questions require running the code or analyzing it with tools that have ground truth.

The split that matters. Use LLMs for descriptions of meaning and intent. Use runtime signals (tests, types, telemetry, traces, type checkers) for behavior. Cross-reference them. When the LLM-generated meaning of a function disagrees with what the runtime says it does, that's a high-signal red flag worth surfacing to a human.

Architecture: the drift detection pipeline

Here's the pipeline I'd build, applying the methodology from section 5.

End-to-end drift detector
The architecture splits LLM work (steps 1, 2, 5, 6) from non-LLM signals (step 3). Storage preserves every snapshot so historical comparisons stay possible. Field-level diffs compare structured outputs rather than freeform prose, which is what makes the comparisons reliable.

Let me walk you through each step and why it's shaped the way it is.

Step 1: extract structure. A single LLM call with a constrained JSON output schema. Input: the diff plus commit metadata. Output: explicit list of changed files, changed symbols, type of change (feature, refactor, bugfix, etc), and one-sentence intent. Low temperature. Validation on output schema. This is your sequential-chain starting point from section 5.

Step 2: semantic profile. For each changed symbol, an LLM call that produces a structured description: role of this symbol in the system, responsibilities it carries, dependencies it relies on, who depends on it, what kinds of inputs and outputs it handles, side effects it has. JSON schema with named fields. Low temperature. This is the LLM acting as a stable observer.

Step 3: behavioral profile. This is the non-LLM step. For each changed symbol, gather actual runtime signals: current type signature, the set of tests that exercise it (and whether they pass), telemetry data if available (call counts, error rates, latencies). This is your ground truth. The LLM never writes this. Your code reads it from your existing infrastructure.

Step 4: versioned store. Persist both profiles, indexed by symbol and commit. Do not overwrite. The whole point of drift detection is comparing to history, which means history has to be preserved. This is a database problem, not an LLM problem.

Step 5: field-level diff. For each symbol that changed, diff the new structured profile against several baseline snapshots from the store. The diff is field-by-field, not freeform text. "Role changed from X to Y. Dependencies added: [list]. Side effects changed: [list]." Structured diffs are what make drift detection robust, because you're comparing in a space where comparison has clear semantics, rather than comparing prose paragraphs that might describe the same thing in different words.

Step 6: classify drift. An LLM call that looks at the structured diff and classifies it: is this drift? What kind (semantic / behavioral / both)? Severity (cosmetic, meaningful, critical)? Possible mitigations? This is where the model's judgment is valuable, because diff classification is exactly the kind of "structured input, structured output" task LLMs handle well.

Step 7: surface to human. Critical or unclear cases go to a human. The pipeline doesn't try to be the final word, it tries to be a high-signal filter that elevates real issues to engineer attention. This is your existence guarantee: when something matters, a human sees it.

Multiple baselines, not just one

A common mistake is comparing only to the previous commit. That misses gradual drift entirely, because each commit looks fine compared to the one before it.

Instead, diff against several baselines simultaneously:

  • Previous commit. Catches immediate regressions and obvious unintended changes.
  • N commits ago (where N is, say, 20 or 50, depending on your commit frequency). Catches medium-term drift that small commits hide.
  • Last "golden" release. Catches long-term drift from a known-good baseline. The drift across this window often reveals the most.
  • Optionally: original commit that created the symbol. Catches the full lifetime of drift from inception.

A function that looks fine vs. the previous commit but looks dramatically different vs. the last release version is the smoking gun for accumulating drift. This is exactly the pattern that one-baseline systems miss.

Q&A pairs as drift fingerprints

You had a specific intuition about Q&A-style "exam" prompting being good for the attention mechanism. I've been validating that throughout this lesson at the prompt-design level. Now I want to validate it at the system-design level, because it has a real role in drift detection.

Here's the idea: at each snapshot, generate a fixed set of canonical Q&A pairs about each symbol. "What does this function do? What does it return for input X? What side effects does it have? What does it assume about its caller?" Same questions, every snapshot.

Now you have a fingerprint. The model's answers to these questions, captured at each commit, are a stable signal of how the model understands the symbol. Drift shows up as the answers to the same questions changing over time.

This has a few nice properties. First, Q&A pairs are easy for the LLM to produce reliably under low-temperature, structured-output conditions. Second, they're directly comparable across snapshots because the questions are fixed. Third, if you ever want to verify the model's claims, you can ask the same questions of the actual code and compare. The Q&A structure is itself the test harness.

So your intuition was right, and it scales from "good way to prompt the model" to "good way to fingerprint code across time." It's the same property of structured-input attention routing, applied at two different levels.

Grounding behavioral claims in runtime signals

This is the most important "what the LLM can't do" point, and it deserves its own subsection.

When the LLM-generated semantic profile says "this function returns the user's discount as a percentage," that's a claim about behavior that the model derived from reading the code. The model could be wrong. Maybe the function actually returns a fraction. Maybe it returns a discount in some cases and null in others.

For behavior, the LLM is a guess. The runtime is the truth.

So in practice, you want to cross-reference. The semantic profile says X. The type signature says Y. The actual test outputs say Z. If all three agree, great. If they disagree, you have either a documentation problem, a type problem, or a test problem, and that's exactly the kind of misalignment worth knowing about.

Concrete examples of runtime signals worth feeding into the behavioral profile:

  • Type signatures (from your type checker, not the LLM's reading of the code).
  • Test cases that exercise the symbol, with their pass/fail status.
  • Telemetry like call counts, latency percentiles, error rates, error types.
  • Traces of actual production calls if you have them, showing the shape of real inputs and outputs.
  • Static analysis output: lint warnings, dead code analysis, dependency graphs.

None of these involve the LLM. All of them give you ground truth that the LLM's semantic claims can be checked against. The combination is what makes the system robust.

Why noise is real, and how to handle it

One thing that will bite you if you don't account for it: LLM-generated descriptions are not perfectly deterministic. Even at temperature 0, the same input can produce slightly different outputs (due to numerical precision in the sampling step, or to whatever non-determinism is in the serving infrastructure). Same code, different runs, you'll get descriptions that differ in their phrasing even though they describe the same thing.

If your drift detector compares prose, you'll get false positives from this noise alone. The function didn't change, but the description got worded differently, and now your diff system says "drift detected."

Same code, different runs, noise in unstructured descriptions
Run 1 (freeform)
This function validates user credentials by checking the password hash and confirming the account is active. It returns a User object on success.
Run 2 (freeform)
Validates a user's login by comparing password hashes and ensuring the account hasn't been disabled. Returns the authenticated User instance.

Same function. Same prompt. Two runs. The prose differs in phrasing while saying the same thing. A naive text diff would flag this as drift. It is not drift.

Run 1 (structured)
role: "authentication"
side_effects: []
returns: "User | null"
deps: ["hash_check", "user_db"]
Run 2 (structured)
role: "authentication"
side_effects: []
returns: "User | null"
deps: ["hash_check", "user_db"]
Structured outputs are far more deterministic because the output distribution is narrowed. The field-level diff is now meaningful: if any field changes, that's a real signal worth investigating. This is why structured outputs aren't just a nice-to-have, they're the foundation of reliable drift detection.

This is one more reason structured outputs matter at every step. The field-level diff is meaningful precisely because the space of legal outputs is narrowed. When a structured field actually changes, that's real signal. When prose phrasing changes, that's noise.

Drift detection is just composed prior sections

Now look back at what we built. Every part of the drift detection architecture is something we covered earlier:

  • From section 1 (the substrate): the model is a context-to-distribution function with no persistent memory. We rely on this by storing snapshots externally instead of expecting the model to "remember" past versions.
  • From section 2 (conditioning): structured prompts with explicit fields make outputs more stable. We use this everywhere we ask the model for a description, classification, or diff judgment.
  • From section 3 (CoT): for the classify-drift step, we let the model reason about the structured diff before emitting a classification. The reasoning is text we can audit.
  • From section 4 (reflection): for critical drift flags, we run an adversarial second-model pass to check whether the classification holds up under skeptical scrutiny.
  • From section 5 (pipelines): the whole architecture is a sequential chain with validators between steps, ground-truth checkpoints (the runtime signals), and tight context per step. It's also the place where error amplification math determines whether your system is reliable at scale.

You're not building something exotic. You're composing primitives. Once you see drift detection as "structured semantic descriptions, stored versioned, diffed field-by-field, cross-referenced with runtime ground truth, classified by an LLM under low temperature," it's just an instance of the same methodology we built up across the prior sections.

What I'd build first

If I were starting from scratch today, this would be my order.

  1. Define the structured JSON schema for the semantic profile. Just a handful of fields: role, responsibilities, dependencies, side effects, contract. Iterate on the schema by running it against five or ten real symbols in your codebase and asking "is this capturing what I'd want to track over time?" Lock the schema before building anything else.
  2. Build steps 1, 2, and 4 (extract, semantic profile, versioned store). Run them across your existing commit history if you can. You now have a versioned trace of semantic descriptions.
  3. Build step 5 (field-level diff) and look at the output for a few symbols you know well. Does it surface drift you recognize? Does it produce false positives? Tune the schema or the diff rules based on what you see.
  4. Add step 6 (LLM classification of diffs). Validate on the same symbols.
  5. Add step 3 (behavioral profile from runtime signals). This is independent and can land in parallel; integrating it makes everything more robust.
  6. Step 7 is the dashboard. Build it last, once the upstream pipeline is producing real signal.

Start narrow. One repo, a handful of symbols, one type of drift. Make that reliable. Expand from there. The classic mistake with systems like this is trying to build everything at once and ending up with a pipeline where every step is 70% reliable, which means end-to-end you're at 70%^7 = 8%. Reliability beats completeness, every time.

Section 07

Recap and next steps

If you ever come back to this site weeks from now and need to re-anchor yourself in a few minutes, this section is for you. Each subsection below compresses one earlier section into its core idea. Then I've left some pointers for what to read or build next.

The six core ideas, compressed

1. The substrate

Text becomes tokens becomes vectors. Each transformer layer lets every token attend to every other token (causally, only to itself and prior tokens) and pull information from the ones it cares about, using a Q/K/V mechanism that's basically a search engine. Many layers stacked means information mixes across positions progressively. The model generates one token at a time by sampling from a probability distribution that's a function of the entire context so far. Between tokens, the model has no memory except the text itself.

2. Prompting as conditioning

Prompting is not asking. It's shaping the next-token probability distribution by constructing the context the distribution is conditioned on. Once you see it this way, system prompts, few-shot examples, persona prompts, and step-by-step instructions all become predictable consequences of how the model uses context, not a bag of tricks. Position matters (start and end are stronger). Structure matters (headers, tags, named fields route attention more reliably than unstructured prose).

3. Chain of thought

CoT is using text as external memory and giving the model more compute per question. Each reasoning token is another full forward pass, and each new token gets to attend to all the previous reasoning. Good chains have explicit labeled steps and concrete intermediate results that attention can route to. Bad chains have vague middle steps and produce confidently wrong final answers. CoT fails through plausible-wrong reasoning, unfaithfulness (decoration that's not actually how the answer was chosen), and sensitivity to phrasing.

4. Reflection

The generate-critique-revise pattern. Works because critique-shaped prompts shift the distribution toward evaluation, and because the initial answer becomes inspectable text in the context. Fails sycophantically when vague critiques cause the model to defend its own wrong answers. Mitigations: adversarial framing, explicit criteria, different model or persona for the critique, external verification for high-stakes correctness.

5. Pipelines and agents

Multi-call architectures where outputs feed forward. Standard patterns: sequential, map-reduce, router, verifier loop, RAG, tool-use loop. Agents are pipelines where the model decides the next step. Methodology: narrow steps, structured outputs, validation between steps, tight context per step, deliberate temperature, log everything, test diverse inputs. Error amplification is the silent killer: 90% per step over 5 steps is 59% end-to-end. The biggest lever is making each step more reliable, not shortening the pipeline.

6. Drift detection

Two kinds of drift: semantic (meaning changes) and behavioral (runtime changes). LLMs are good at semantic descriptions, not behavioral predictions. The architecture: extract structure, generate structured semantic profile, separately gather behavioral signals from runtime, store everything versioned, field-level diffs against multiple baselines, LLM classification of diffs, surface to humans. Structured outputs (not prose) are what makes the comparisons reliable. Q&A pairs work as drift fingerprints. Everything in this lesson composes into this one applied architecture.

What to read next

Sorted from most foundational to most applied. Pick based on what you want to push deeper on.

To go deeper on the substrate

  • "Attention Is All You Need" (Vaswani et al., 2017). The original transformer paper. Dense, but worth reading once you have the intuition we built in section 1. The math is more readable than people think once the picture is in your head. arxiv.org/abs/1706.03762
  • "The Illustrated Transformer" by Jay Alammar. The classic visual walkthrough. If you ever want to refresh on the mechanics with diagrams, this is the most-recommended resource for a reason. jalammar.github.io/illustrated-transformer
  • 3Blue1Brown's neural network and transformer videos. Visual, intuitive, paced. The "But what is a GPT" video is exceptionally good. youtube.com/@3blue1brown

To go deeper on prompting and CoT

  • "Chain-of-Thought Prompting Elicits Reasoning in Large Language Models" (Wei et al., 2022). The paper that put CoT on the map. Worth reading specifically for how experiments were structured. arxiv.org/abs/2201.11903
  • Anthropic's prompt engineering documentation. Concrete, structured, recently updated. Good for the practical side. docs.claude.com/.../prompt-engineering
  • "Lost in the Middle: How Language Models Use Long Contexts" (Liu et al., 2023). The paper behind the position-matters claim in section 2. Empirical and clarifying. arxiv.org/abs/2307.03172

To go deeper on reflection

  • "Self-Refine: Iterative Refinement with Self-Feedback" (Madaan et al., 2023). The reflection-as-iteration paper. Good baseline for the pattern. arxiv.org/abs/2303.17651
  • "Large Language Models Cannot Self-Correct Reasoning Yet" (Huang et al., 2023). The counterpoint. Important for understanding the sycophantic failure mode at a research level rather than just folklore. arxiv.org/abs/2310.01798

To go deeper on pipelines and agents

  • Anthropic's "Building Effective Agents" post. The conceptual map for the patterns we covered. The vocabulary for the spectrum (workflow vs. agent) comes from this and adjacent thinking. anthropic.com/research/building-effective-agents
  • ReAct: "Synergizing Reasoning and Acting in Language Models" (Yao et al., 2022). The tool-use-with-reasoning pattern that underlies many modern agents. arxiv.org/abs/2210.03629
  • The DSPy framework documentation. If you ever want to take pipeline construction seriously and treat prompts as something you compile rather than write, DSPy is worth knowing about even if you don't adopt it. dspy.ai

For your codebase system specifically

  • The "ast-grep" tool and tree-sitter. If you're not already using tree-sitter to walk code structure, it pairs extremely well with LLM-based analysis. You get cheap reliable structural facts from tree-sitter and reserve the LLM for meaning.
  • "Code as Policies" and the broader literature on code-understanding LLMs. A lot of recent research is directly relevant to what you're building. Anthropic, GitHub, and Sourcegraph all publish in this space.
  • Property-based testing tools (Hypothesis for Python, fast-check for JS). A good source of runtime signals for the behavioral profile. Property tests give you a much richer behavioral fingerprint than example-based tests.

One last thing

Everything in this lesson sits on a single observation: the model is a function from context to probability distribution. Everything you build, every prompt you write, every pipeline you architect, they all reduce to "construct the right context." Once that view is internalized, things stop being magic.

If you want, when you're working on your codebase system and run into a part of the LLM behavior that feels weird, walk it back to that question. "What's in the context at this point, and what next-token distribution does that produce?" The answer is almost always there.

Good luck with the system. Send me follow-ups when things break in unexpected ways. The interesting failure modes are how you learn the rest.
