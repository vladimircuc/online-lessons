BI4: 1. The Internet

The internet is a network of networks. It connects billions of devices worldwide using standardized, open protocols.

Key Facts

  - The internet is decentralized: no single entity owns or controls it
  - It uses open (non-proprietary) protocols so any device
    from any manufacturer can connect
  - Devices are identified by IP addresses
  - Data travels as packets through multiple routes
  - The World Wide Web (websites) runs ON the internet
    but is NOT the same thing as the internet
  - Other things that use the internet: email, streaming,
    gaming, file transfer, IoT devices

Internet vs World Wide Web

Internet:  The physical network infrastructure
           (cables, routers, servers, protocols)
           
WWW:       A system of linked web pages accessed
           through browsers using HTTP/HTTPS
           
The WWW is a SERVICE that runs on the internet.
Email, streaming, and gaming also run on the internet
but are NOT part of the WWW.

BI4: 2. Protocols

A protocol is a set of rules that devices follow to communicate. The internet depends on layered protocols working together.

The Protocols You Need to Know

ProtocolWhat It Does
IP (Internet Protocol)Assigns addresses to devices and routes packets across networks. Every device gets a unique IP address (like a mailing address). IPv4 uses 32 bits (about 4.3 billion addresses). IPv6 uses 128 bits (virtually unlimited addresses).
TCP (Transmission Control Protocol)Ensures reliable delivery. Breaks data into packets, numbers them, sends them, checks that all arrived, and reassembles them in order. If a packet is lost, TCP resends it.
HTTP / HTTPSRules for requesting and serving web pages. HTTPS adds encryption (TLS/SSL) so data between browser and server is private. The "S" = Secure.
DNS (Domain Name System)Translates human-readable domain names (like google.com) into IP addresses (like 142.250.80.46). It's the "phone book" of the internet.

How They Work Together

You type "google.com" in your browser:

1. DNS converts "google.com" → IP address 142.250.80.46
2. TCP breaks your request into numbered packets
3. IP  routes each packet across the network
4. Packets may take different paths to reach Google
5. TCP at Google reassembles packets in order
6. Google sends the web page back the same way
7. HTTPS encrypts everything so no one can eavesdrop
TCP vs IP: Think of IP as the addressing system (where to send it) and TCP as the delivery guarantee (making sure it all arrives correctly). IP handles routing, TCP handles reliability.

Quick Check: Protocols

What does DNS do? Why is it necessary?
DNS translates domain names (google.com) into IP addresses (142.250.80.46). It's necessary because humans remember names but computers communicate using numbers. Without DNS, you'd have to memorize IP addresses for every website you visit.

BI4: 3. Packets & Routing

Packet Switching

When you send data across the internet:

1. Data is broken into small packets
2. Each packet contains:
   - A piece of the data
   - Source IP address (where it's from)
   - Destination IP address (where it's going)
   - Sequence number (so it can be reassembled)
3. Packets travel independently
4. Different packets may take different routes
5. They may arrive out of order
6. TCP reassembles them using sequence numbers

Why packets?
  - Efficient: multiple users share the same wires
  - Resilient: if one route fails, packets reroute
  - Fair: no single user monopolizes the connection

Routing

Routers are devices that direct packets toward their destination. They make decisions at each hop about the best path based on current network conditions.

Your packet: A → Router1 → Router5 → Router8 → B
Another packet from the SAME message might go:
              A → Router2 → Router6 → Router8 → B

Different paths, same destination.
TCP puts them back together at the end.

Quick Check: Packets

Why can packets from the same message arrive out of order?
Because packets travel independently and may take different routes through the network. Some routes are faster or less congested, so packets sent later might arrive first. TCP handles this by using sequence numbers to reassemble everything in the correct order at the destination.

BI4: 4. Fault Tolerance

Definition

A system is fault-tolerant if it continues to function even when part of it fails. The internet is designed to be fault-tolerant through redundancy.

How the Internet Achieves Fault Tolerance

Redundancy: Multiple paths between any two points.
If one cable, router, or server fails,
data can take an alternate route.

Example network:
  A -------- B
  |  \       |
  |    \     |
  C -------- D

If the A-B connection breaks:
  A → C → D → B  (alternate route exists)
  
The network is fault-tolerant because
there's no single point of failure.

Single Point of Failure

If removing ONE connection makes it impossible
for some devices to communicate, that connection
is a single point of failure.

NOT fault-tolerant:
  A --- B --- C
  If B fails, A and C are disconnected.
  B is a single point of failure.

Fault-tolerant:
  A --- B --- C
  |           |
  +-----------+
  Now if B fails, A and C still connect directly.
Common exam question: They show you a network diagram and ask "if connection X is removed, can device A still reach device D?" Trace alternate paths. If NO alternate path exists, the network is NOT fault-tolerant for that failure.

Quick Check: Fault Tolerance

Network: A --- B --- C | | D --- E --- F A also connects to D. C also connects to F. If the B-C connection fails, can A still reach C?
Yes. Multiple alternate routes exist: A → D → E → F → C A → B (B still works, just B-C is broken) → but B can't reach C directly... So: A → D → E → F → C is the alternate path. The network is fault-tolerant for this failure because redundant connections exist.

BI4: 5. Parallel & Distributed Computing

Sequential vs Parallel

Sequential: Tasks done one after another.
  Task A (10 sec) → Task B (10 sec) → Task C (10 sec)
  Total: 30 seconds

Parallel: Tasks done at the same time.
  Task A (10 sec) ┐
  Task B (10 sec) ├→ All finish in 10 seconds
  Task C (10 sec) ┘
  Total: 10 seconds (if they're independent)

Speedup and Its Limit

Speedup = Sequential time / Parallel time

But there's a catch: some tasks are sequential
(they depend on previous tasks finishing first).

Example:
  - Pour foundation: 5 hours (must be first)
  - Build walls: 3 hours (needs foundation)
  - Paint walls: 2 hours (needs walls)
  Total sequential: 10 hours

  You CAN'T parallelize these because each
  step depends on the previous one.

  But if you have 4 INDEPENDENT walls to paint:
  Sequential: 8 hours (2 hours each, one at a time)
  Parallel (4 painters): 2 hours

Key point: Speedup is limited by the sequential
portion. Even with infinite processors, the
sequential parts take the same time.

Distributed Computing

What: Splitting a large task across multiple
       computers connected by a network.
Example: SETI@home (searching for alien signals
         using thousands of home computers)
Benefit: Can solve problems too large for any
         single computer.
Challenge: Communication overhead between machines,
           coordination complexity, network latency.

Quick Check: Parallel Computing

A task has two parts: Part A: 20 seconds (must run first) Part B: 4 independent subtasks, each 10 seconds. Sequential total time? Parallel total time (4 processors for Part B)?
Sequential: 20 + (4 * 10) = 60 seconds Parallel: 20 + 10 = 30 seconds (Part A still takes 20 sec, can't parallelize. Part B: 4 subtasks run simultaneously in 10 sec.) Speedup = 60/30 = 2x Note: even with 100 processors, Part A still takes 20 seconds. That's the limit.

BI1: 6. Collaboration & Program Design

Collaboration in Programming

Benefits of working in teams:
  - Diverse perspectives catch more bugs
  - Different skills complement each other
  - Code review improves quality
  - Pair programming: one types, one reviews
  - Larger projects become manageable

Collaboration tools:
  - Version control (Git/GitHub)
  - Shared documents
  - Code review platforms
  - Project management tools

Program Purpose vs Function

Purpose:   The PROBLEM the program solves.
            WHY it exists. Who it's for.
            Example: "Help students organize
            homework deadlines."

Function:  WHAT the program actually does.
            The specific behavior.
            Example: "Sorts tasks by due date
            and displays urgent ones in red."

Purpose = the big picture goal
Function = the technical behavior
For the written response: The exam may ask about your program's purpose. Purpose is about the PROBLEM you're solving and WHO it helps, not just what the code does technically.

BI1: 7. Error Types

Three types of errors. The exam will describe a scenario and ask which type it is.

The Three Error Types

1. Syntax Error
   The code violates the language's grammar rules.
   The program cannot run at all.
   
   Examples:
   - Missing parenthesis: print("hello"
   - Misspelled keyword: whille instead of while
   - Missing colon: if x > 5
   
   Caught by: the interpreter/compiler BEFORE running

2. Logic Error
   The code runs without crashing but produces
   wrong results.
   
   Examples:
   - Using + instead of * in a formula
   - Off-by-one error in a loop (< instead of <=)
   - Checking the wrong condition in an IF
   
   Caught by: testing and comparing actual vs expected output

3. Runtime Error
   The code starts running but crashes midway
   due to an operation that can't be completed.
   
   Examples:
   - Dividing by zero
   - Accessing an index that doesn't exist
   - Running out of memory (infinite loop)
   
   Caught by: the program crashes with an error message
Logic errors are the hardest to find because the program doesn't crash or give an error message. It just quietly gives the wrong answer. The only way to catch logic errors is to test thoroughly and compare output to expected results.

Quick Check: Error Types

A program calculates the average of a list by dividing the sum by the length. But the list is empty (length = 0). What type of error occurs?
Runtime error (division by zero). The code is syntactically correct (no grammar errors) and the logic is correct for non-empty lists. But when the list is empty, dividing by 0 causes the program to crash at runtime. Fix: check if the list is empty before dividing.
A program is supposed to count numbers greater than 50 in a list. It uses: IF (num > 500) instead of IF (num > 50) What type of error?
Logic error. The program runs fine, no crashes, no error messages. But it counts numbers greater than 500 instead of 50. The output is wrong (too few counted). This is a typo in the logic, not in the syntax. The code is valid, just incorrect.

BI1: 8. Iterative Development & Testing

Iterative Development

The cycle:
  Plan → Design → Code → Test → Evaluate → Repeat

Key principles:
  - Build in small increments, not all at once
  - Test after each increment
  - Get feedback and refine
  - Don't try to build the entire program in one pass
  - Each iteration improves on the previous one

Testing Strategies

Boundary testing:
  Test at the edges of expected input.
  If a function works for ages 0-120:
    Test: 0, 1, 119, 120 (boundaries)
    Test: -1, 121 (just outside boundaries)

Edge cases:
  - Empty list
  - Single element list
  - Very large numbers
  - Negative numbers when expecting positive

Normal cases:
  Test typical expected inputs to verify
  the basic functionality works.

Debugging:
  - Add DISPLAY statements to see variable values
  - Trace through code manually line by line
  - Test small sections independently
  - Use a systematic approach, not random guessing

Program Documentation

  - Comments explain WHY, not just WHAT
  - Good: // Check if user is old enough to vote
  - Bad:  // Check if age >= 18 (just restates the code)
  - Documentation helps others understand your code
  - Documentation helps FUTURE YOU understand your code

Quick Check: Development

A program should accept ages 0-120. Which test cases should you use to thoroughly test the input validation?
Boundary cases: 0, 120 (valid edges) Just outside: -1, 121 (should be rejected) Normal case: 25 (typical valid input) Edge cases: very large number (99999), negative number (-50), non-integer if applicable (12.5) Testing only "normal" inputs like 25 is insufficient. You must test boundaries and invalid inputs to be thorough.
