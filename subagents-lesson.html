Section 01

The one idea everything rests on

Let's start with the single idea the whole topic hangs off, in two sentences. A subagent is a second instance of Claude that runs in its own separate context window, does a chunk of work, and reports back a summary. You reach for one because a single long session slowly fills with clutter and starts to lose the thread.

Hold onto those two sentences. Everything else here, the tool limits, running several at once, the autonomy controls, is just detail hanging off them.

The core idea

Your context window is not infinite. A subagent is how you do heavy, noisy work somewhere else and bring back only what matters.

Section 02

How Claude's memory actually works

Most explanations stop at "the context window fills up." If you understand the layer underneath, the rest is obvious, so let's go one level deeper.

A language model has no memory between turns. It is stateless. The entire mind it has at any moment is whatever sits in its context window: the instructions, every earlier message, every file it read, every tool result, every dead end it explored. There is nothing else. Two things follow from that, and both matter.

First, the window is finite. There's a hard ceiling on how much text fits, and a long session marches toward it. Second, and this is the part people miss, quality slips well before you hit that ceiling. The model's attention is a limited resource spread across every token in the window. When the window is short and focused, attention concentrates on what matters. As it fills with thousands of tokens of search output, file dumps, and reasoning you no longer care about, the signal you want gets diluted, and a decision made an hour ago is now buried far from where the model is reading. Answers get vaguer, earlier choices get forgotten, and code starts drifting from the patterns you set.

A way to picture it: imagine holding a careful conversation in a room where every word anyone has ever said is still being shouted in the background. You can technically still hear, but you're working harder and missing things. A subagent sends the noisy work into a soundproof room next door, and only a short written summary comes back out.

Same amount of work, two outcomes. Without subagents the window fills with noise and the useful signal gets buried. With subagents, the heavy work runs in separate windows and only small summaries (teal) come back, so the main thread stays lean and sharp.

Section 03

What a subagent really is

This is the piece worth slowing down on, because the natural assumption is wrong. It's tempting to think of a subagent as "another part of the same conversation." It is not. It is a fresh, separate run of the model.

When the main agent decides to delegate, it spawns the subagent and a brand new context window is created for it. That window is sealed off, but it is not empty: the subagent gets its own instructions, the task description the main agent writes for it, and some basics like your project rules. What it does not get is the conversation history or the files the main thread already read. It starts fresh on the task itself.

The subagent then runs its own loop, reading, searching, editing, running commands, entirely inside its own window. When it finishes, it sends back exactly one thing: a final result message. All of its messy intermediate work stays in its window and never enters the main conversation. The main agent reads that one message and carries on.

Section 04

The one rule: the boundary

If you remember one picture from today, make it this one, because it explains almost every behaviour you'll ever see. A subagent has exactly one channel in and one channel out.

In: only the task prompt the main agent writes. Out: only the summary it returns. Nothing else crosses the boundary.

What this one rule explains

Why a subagent "doesn't know" something you just discussed. The conversation never crossed the boundary. The only thing that reaches it is the prompt, so if it needs a file path, an error message, or an earlier decision, that has to be written into the prompt. Think of it like a contractor who just walked in the door and knows nothing about the project until you brief them.

Why ten parallel subagents that each return a long report defeat the point. All ten reports come back across the "out" channel into your main window, and you've just refilled the clutter you were trying to avoid. The fix is to have them return tight summaries, not full transcripts.

Why two subagents can't coordinate with each other mid-task. There's no channel between them, only back to the parent. When you do want workers that message each other, that's a separate feature we'll meet later called agent teams.

The exception that proves the rule

A "fork" is a subagent that inherits the whole conversation instead of starting fresh, so it needs no briefing. Its own work still stays out of your main window. The default subagent is sealed and must be briefed; a fork comes pre-loaded.

Section 05

What crosses the line

Since the boundary is the whole game, here is exactly what a subagent starts with and what it doesn't. Keep this in mind whenever you write a task for one.

It does start with

  • Its own instructions, the persona and rules you gave it
  • The task prompt the main agent writes
  • Your project's standing rules and standards

It does not get

  • The conversation you've had so far
  • The files Claude already opened in the main thread
  • What you were thinking but never wrote down

The practical takeaway: a good delegation prompt is specific. Name the files, paste the error, state the decision. The subagent can be brilliant, but only about what you actually told it.

Section 06

The five things you configure

Once you have the boundary in your head, the settings stop feeling arbitrary. There are basically five dials on a subagent, and each one maps to a clear reason.

01 · its instructions

The specialist's brain

The system prompt is where you write who it is, what to check, and how to report. This is how you get focused, consistent, expert behaviour instead of a generic helper.

02 · tools

What it can do, and safety

You decide which tools it can touch. A reviewer with read-only tools literally cannot change your files, so the limit is both a focus and a safety guarantee.

03 · model

Cost versus power

Point a "search the whole codebase" worker at a fast cheap model, and a hard reasoning task at a stronger one. You pay for power only where it earns its keep.

04 · permissions

How far it goes alone

This is the autonomy dial: ask before everything, auto-accept edits, or run with fewer prompts. We'll spend a whole session on this one later.

05 · context mode

Sealed, or pre-loaded

By default it starts fresh and sealed, which keeps things clean but means you must brief it. A fork instead inherits the whole conversation, so there's no briefing needed. Same trade-off we just covered, now as a setting you choose.

Every dial shapes one of three things: what the specialist knows, what it can do, or what it costs.

Section 07

Built-in versus custom

Here's the good news: you're already using subagents without setting any up. Claude Code ships with a few built in and reaches for them on its own. You'll see this live in the demo, when you ask a broad question and watch it quietly spin one up.

built in

Explore

A fast, read-only worker for searching and understanding a codebase. Keeps all that search output out of your main window.

built in

Plan

A read-only researcher that gathers context while Claude is forming a plan, before any code gets written.

built in

General-purpose

The full toolkit, for multi-step jobs that need both exploring and acting. The do-anything worker.

When to build your own

A custom subagent is something you make when you keep needing the same specialist with the same instructions. That repetition is the real signal. A simple rule of thumb: if you've set up the same kind of worker by hand three times, turn it into a custom subagent so you never do it again.

Section 08

When to use one, when not to

This judgment is what separates using subagents well from spraying them everywhere. They are a tool with a cost, not a default.

Reach for a subagent

work that belongs in its own room

  • It produces a pile of output you won't reread: tests, logs, docs, exploring a subsystem
  • You want a hard guardrail, like a strictly read-only investigation
  • The work is self-contained and a summary is all you need back
  • The same specialist task keeps coming up
  • Several independent investigations can run at the same time

Stay in the main thread

work that needs to stay close

  • The task needs constant back-and-forth and refining
  • Several steps all share the same heavy context
  • It's a quick, targeted edit, a subagent starts cold so it's slower here
  • It's a question about something already in your conversation

The honest trade-off: a subagent always starts from nothing and has to find its bearings. For small fast changes that makes it slower, not faster.

Section 09

Subagents versus skills

This is the question you'll naturally ask next: how is a subagent different from just giving Claude a reusable instruction, a skill? The whole answer is the context boundary.

Same window or a separate one. That single difference decides which tool you want.

So the rule is short. Want a reusable prompt that works on whatever is already in front of you? That's a skill. Want noisy or self-contained work done elsewhere with only a summary coming back? That's a subagent.

Section 10

A worked example

Let's tie every thread together with the one we'll build live: a code reviewer. It has read-only tools, so it can inspect but never touch your files. Its instructions say it's a senior reviewer, give it a checklist, and tell it to report findings by priority.

One small example shows all of it: isolation, custom instructions, a tool limit, delegation, and a summary returning across the boundary.

When you finish a feature you simply say, "have the code reviewer look at my recent changes." It reads the diff in its own sealed window, runs its whole analysis there, and hands back one prioritized list. Your main session never fills with the full diff or the reviewer's reasoning, and because its tools are read-only you never worry it'll quietly "fix" something behind your back.

Section 11

The bigger picture

Subagents can run several at once, each in its own window, and Claude pulls the findings together. As your goals grow toward running things in parallel and more hands-off, two related ideas take over. It's worth knowing the difference so you don't mix them up, even though we'll only go deep on them in later sessions.

today's focus

Subagents

Workers inside one session. The foundation everything else builds on, and where we'll start in the demo.

later

Background agents

Many independent sessions running at once, which you watch and manage from one place.

later

Agent teams

Separate sessions that can message each other, for work that needs real coordination between workers.

Your goal of a main agent and helpers working in parallel on their own starts here, with subagents in one session, and grows into the other two as the work gets bigger.

Section 12

Check your understanding

Five quick ones. Pick an answer and the reasoning appears underneath. No pressure, this is just to make the ideas stick before we go hands-on.

Question 1

What is the main reason to use a subagent?

It's about protecting context. A subagent does noisy work in its own window so the main thread stays lean and sharp. It isn't a speed trick, in fact a subagent starts cold and is often slower for small jobs, and running many of them can use more tokens, not fewer.

Question 2

From your conversation, what is the only thing that reaches a subagent?

Only the task prompt crosses the boundary. The subagent also has its own instructions and your project rules, but nothing from the conversation itself reaches it except what the main agent writes into the prompt. That's why you have to name files and paste errors explicitly.

Question 3

Why can it backfire to run ten parallel subagents that each return a long, detailed report?

The summaries all land back in the main window. If each one is long, you've refilled the exact clutter the subagents were supposed to keep out. The fix is to ask for tight summaries rather than full transcripts.

Question 4

When is the main conversation the better choice over a subagent?

Quick edits belong in the main thread. A subagent starts from nothing and spends time getting its bearings, so for a small fast change that cold start isn't worth it. The other three are exactly the cases where a subagent shines.

Question 5

What is the key difference between a skill and a subagent?

A skill stays in the same window. It injects reusable instructions into the conversation you're already in. A subagent is the opposite: it does its work in a separate window and only the result comes back.
